# 开发规范

本文规定项目通用的 ECS、调度、注释和日志要求，并提供构建与调试入口。功能专项约束从 [Bevy App 与项目模块](architecture/README.md) 查找，项目状态、时钟与公共调度契约见 [应用流程](architecture/game_flow.md)。测试选择与覆盖边界见 [测试指南](testing/README.md)。

## 技术栈与版本

项目统一使用 [rust-toolchain.toml](../rust-toolchain.toml) 固定的 nightly。在仓库目录运行 rustup 管理的 Cargo 会选择该版本。Rust edition 见各应用清单，workspace 成员、共享依赖和构建参数见 [Cargo.toml](../Cargo.toml)，实际依赖版本见 [Cargo.lock](../Cargo.lock)。

固定工具链包含 `rustfmt`、`clippy` 和 `rust-src`。

API 行为以对应版本的官方文档为准，示例必须匹配项目版本。

## ECS 的职责划分

### Entity：实体只表示身份

- 使用 Bevy 的 `Entity` 标识实体，通过组件组合表达其能力和状态。
- 项目代码创建的运行时实体及其子实体必须在初始组件或场景组合中提供非空 `Name`；BSN 的 `#name` 和 required 组件提供的名称均可，创建后补名不满足要求。测试 fixture、第三方内部实体和导入资产内部节点不受此项约束。
- 实体之间的引用只使用 Bevy 关系组件，由 Bevy 维护反向索引，不使用普通 `Entity` 字段保存跨实体关联，也不持有其他实体组件的长期引用。

### Component：组件承载实体数据

- 实体自身的状态定义为 `#[derive(Component)]` 的结构体或枚举；无数据的身份或能力标签使用标记组件。
- 按数据职责、访问模式和生命周期拆分组件，保持内聚。避免把位置、生命值、输入、渲染和 AI 等无关状态堆进一个巨型组件，也不要机械地将每个字段拆成组件。
- 组件可以提供构造、校验和只操作自身数据的辅助方法。每帧更新、跨实体交互、访问世界或外部服务等行为应由系统执行。
- 通过组件组合复用能力，避免用继承式层级或大型对象类型分支模拟实体种类。
- 同一业务状态应有明确的数据来源；优先复用 Bevy 已有组件，例如 `Transform`，避免无必要地维护重复数据。

### Resource / Local：明确共享范围

- 全局唯一、由多个系统共享的数据使用 `#[derive(Resource)]`，通过 `Res<T>` / `ResMut<T>` 访问。
- 属于某个实体的数据放在组件中。
- 仅供单个系统保存的临时状态可使用 `Local<T>`。

### System：系统实现行为

- 系统使用职责明确的 Rust 函数，通过 `Query`、`Res`、`ResMut`、`Commands` 等参数声明所需数据。
- 使用组件组合和 `With<T>` / `Without<T>` 等过滤条件选择实体，避免依赖实体名称、固定 ID 或无关的类型判断。
- 查询仅请求所需数据；只读访问使用 `&T` / `Res<T>`，确需修改时才使用 `&mut T` / `ResMut<T>`，保留调度器并行执行的空间。
- 一个系统负责一个清晰的数据变换或流程步骤。复杂计算可提取为纯函数，由系统负责数据访问和结果写回。
- 查询访问冲突应通过拆分系统、明确互斥过滤条件或必要的 `ParamSet` 解决，不用 `unsafe` 或随意添加锁掩盖问题。
- 常规业务优先使用普通系统。确需独占 `&mut World` 的系统时，说明原因并限制其范围。

## 场景与 UI 装配规范

- 新增或修改场景、UI 和其他实体层级装配时，尽量采用 BSN（Bevy Scene Notation）风格的声明式代码，清晰表达组件、初始数据和子实体关系。
- 优先使用当前 Bevy 版本支持的 Rust 内嵌 `bsn!` 及可组合场景函数；按职责提取小型可复用结构，减少冗长、重复的逐实体装配代码。具体语法以项目依赖版本的官方文档为准。
- 场景辅助函数只在复用、参数化或独立职责确实提高可读性时提取或保留，否则内联；一次性辅助函数也按这一标准判断。
- BSN 用于声明结构与初始数据；运行时状态变化、输入、交互和逐帧更新通过 ECS 系统或 Observer 实现，保持装配与行为职责清晰。
- 运行时动态构造、第三方 UI（如 Egui 工具面板）或当前 API 不适合 BSN 表达时，可以使用普通 `Commands` 或对应框架的原生 API，并在相关中文注释中简要说明设计原因。

## 调度、通信与生命周期

- 使用 `add_systems` 注册系统。启动初始化使用 `Startup`，逐帧逻辑使用 `Update`；需要固定时间步的模拟逻辑使用 `FixedUpdate`，并使用相应时间步数据。
- 同一 Schedule 内有先后依赖的系统必须通过 `.before()`、`.after()`、`.chain()` 或 `configure_sets` 配置系统集之间的依赖。仅 `.in_set()` 不建立顺序；注册顺序、元组顺序和数据访问冲突也不能代替顺序约束。
- 顺序约束不会自动注册被引用的系统，也不能建立跨 Schedule 的顺序；核对相关系统是否注册，并按实际调度阶段设计数据流。
- 实体生成、销毁及组件增删等结构变更优先使用 `Commands`。它们是延迟操作，不要假设调用后立即能被当前系统的 `Query` 看到。
- 后续系统需要观察结构变更时，确保在两者之间应用延迟命令。常规调度配置中的 `.before()`、`.after()` 和 `.chain()` 支持自动插入同步点；自定义调度需核对实际配置，必要时使用 `ApplyDeferred`。
- 系统间的缓冲通信使用 `Message`、`MessageWriter`、`MessageReader`，并在 `App` 中注册消息；需要触发式响应时使用 `Event` / `EntityEvent` 与 Observer。两者语义不同，使用当前锁定版本的接口。
- `World::trigger` 在调用中触发 Observer；`Commands::trigger` 要等命令应用时才触发，不能假设立即生效。
- 跨系统协作通过组件、资源、消息或显式调度表达，不直接调用另一系统来隐式驱动流程。
- 初始化、退出和实体清理要与实际生命周期对应。默认消息缓冲不会永久保留，条件停用的读取系统可能漏读；必须跨停用期保留的业务状态应存入组件、资源或明确管理的持久队列。

## 代码组织与性能

- 按功能目录组织代码，遵守根 [AGENTS.md](../AGENTS.md) 的单一 Plugin 入口约定；在目录内按职责拆分平铺实现文件，不按组件、系统、资源类型建立横跨功能的杂项目录。
- 各应用入口按用途创建 Bevy `App`，安装玩法插件并选择引擎和工具配置。功能 Plugin 封装本功能所需的数据初始化和行为注册，跨功能顺序使用公开调度集合。[应用装配](architecture/game_flow.md#应用装配) · [共享调度契约](architecture/game_flow.md#调度与模拟边界)
- 无需为小实现或测试预建目录；共用 fixture 保留为功能内的普通函数，不创建仅包装函数的额外 Plugin。
- 项目 crate 在当前编译配置下实际产生的单字段结构体使用具名字段，避免通过 `.0` 访问含义不明确的数据；约束包括声明宏、过程宏、属性宏及派生宏生成的类型，也包括第三方宏在项目 crate 内生成的辅助类型，按宏展开后的最终字段形状判断。无字段标记结构体、多字段元组结构体、枚举变体及依赖 crate 内部类型不受此项限制，源码中的 lint 设置不能关闭此约束。
- 优先批量查询处理实体，避免每帧全世界扫描、无必要的分配与克隆，以及频繁增删组件。
- 在适合的场景使用 `Added<T>`、`Changed<T>`、条件执行或消息驱动减少重复工作；不能因此遗漏必要的连续更新。
- 默认使用 Bevy 的存储与调度方式。只有测量表明确有需要时，才调整组件存储、并行迭代或缓存策略。

### 常量与参数归属

- 为具有独立业务含义的固定值使用语义明确的 `const`，包括玩法阈值、物理参数、数值容差和共享布局尺寸。名称或必要注释说明单位，并区分距离与距离平方、角度与弧度等不同量纲。
- 同一含义的参数在初始化、运行更新和重建路径中使用同一来源；数值相同但含义不同的约束分别命名，不因数值相等就合并。固定模拟频率、渲染限帧和日志采样间隔分别归属各自职责。
- 常量放在拥有该语义的模块或插件内，默认私有，只在实际复用时扩大到 `pub(super)` 或 `pub(crate)`；跨模块使用方引用归属方，不建立无明确职责的集中常量目录。
- 需要运行时调整、按实体变化或持久化的参数继续由对应组件、资源或设置管理；配置默认值和资产清单保留原有数据来源，不另复制一份常量造成不一致。
- 上下文清晰且无独立业务含义的 `0`、`1`、空集合和单位变换等可直接使用字面量，不为消除所有数字而机械提取常量。
- 纯常量提取保持原值、数值类型、单位、浮点运算顺序及比较边界不变；调整参数或行为时按实际变化执行[对应验证](testing/README.md#按变更类型选择检查)。

### 测试代码组织

- 项目 Rust 测试统一放在所属插件的 `src/<插件目录>/tests.rs`，由该插件的 `mod.rs` 使用 `#[cfg(test)] mod tests;` 注册；没有测试的插件无需创建空文件。
- 每个插件只使用这一个测试文件，按职责在文件内用 `mod` 分组；不另建 `*_tests.rs`、测试子目录或生产文件中的内联测试模块。
- 仅供测试的独立 fixture 文件也并入所属插件的 `tests.rs`，跨插件共享的 fixture 由所属插件按需重导出；生产流程中必要的 `#[cfg(test)]` 插桩及其访问接口保留在其行为发生的位置。

## 中文注释规范

- 新增或修改的代码应有必要的中文注释，说明模块、组件、资源和系统的职责，以及关键流程、边界条件和设计原因。代码标识符、API 名称和必要的英文术语保留原文。
- 日志消息、结构化字段名，以及代码定义的状态值、原因和错误提示统一使用英文；外部错误信息和文件路径保留原文。
- 遵循 Rust 注释格式：普通实现说明使用 `//`，类型、函数等条目的文档注释使用 `///`，模块或 crate 的文档注释使用 `//!`；文档注释放在对应条目的属性之前，模块文档注释放在模块开头。
- 对外公开的接口使用中文文档注释说明用途；必要时补充参数含义、返回值、错误条件和 panic 条件。文档中的代码示例使用 Rust 代码块，并与实际接口保持一致。
- 注释简洁、明了、直白，优先解释“为什么这样做”和不明显的行为；不逐行复述代码，不写空泛套话，不为显而易见的赋值或调用添加注释。
- 调度依赖、延迟命令的可见时机、日志与存档的处理规则等不易从代码看出的约束，应在相关位置用简短中文说明。
- 修改代码时同步更新相关注释，删除失效或误导性的说明，确保注释与实际行为一致。

## Git 提交规范

- 提交标题遵循 Conventional Commits 格式 `<type>[optional scope]: <description>`；标题语言按用户明确要求或仓库现有惯例确定，`type` 和 `scope` 保留英文。
- 提交正文统一使用中文，简洁说明具体改动、原因和必要影响；代码标识符、API 名称、文件路径及必要的英文术语保留原文。
- 正文不写验证结果、测试数量、截图或临时记录位置，以及未运行、待验收、验证受阻等执行说明。新增测试、校验工具或验收文档属于改动，可描述其用途和覆盖范围。
- 验证执行记录放在交付说明或对应 Issue／PR。
- `BREAKING CHANGE`、`Refs`、`Closes` 等固定页脚标记保留原文；附带的自然语言说明使用中文。

## 游玩日志与调试

- 新增或修改功能时，补充关键状态变化、交互及持久化操作的原因、结果和失败日志，以便复现问题。
- 状态变化日志应包含时间、级别、模块或系统、相关实体或业务 ID、变化前后值和触发原因；错误日志应包含操作、相关文件路径及错误信息，方便定位问题。
- 使用统一的日志设施，将 Bevy 日志与业务日志写入会话文件。日志配置和写入职责集中管理，避免各系统自行打开文件或重复初始化日志设施。
- 关键流程、状态变化和错误默认落盘；详细调试信息使用合适的日志级别。连续变化的高频数据按需采样或汇总，避免逐帧记录全部组件，但不能漏掉有调试价值的离散状态变化。
- 不要将日志用作存档。未经用户要求，不自动删除历史日志。

## 构建与调试

### 开发构建

在仓库根目录执行：

```powershell
cargo build --locked
```

工作区默认构建普通游戏。Windows 输出程序为 `target/debug/demo.exe`。开发构建保留调试信息，但优化可能使单步调试跳行或令部分变量不可查看。首次构建依赖耗时较长，后续构建可以复用缓存。[世界检查器](../README.md#运行) · [应用验收](testing/README.md#自动化启动准备)

### 发布构建

```powershell
cargo build --release --locked
```

Windows 输出程序为 `target/release/demo.exe`。发布构建保留默认 panic 行为，便于正常清理资源和处理线程异常；两种构建模式的优化与调试参数以 [Cargo.toml](../Cargo.toml) 为准。

`--locked` 确保使用提交的依赖锁定文件，需要变化时直接报错。构建参数以 Cargo 文件为准。发布包必须携带完整的 `assets/`。

各应用共用[构建脚本](../apps/build.rs)。脚本为编译期嵌入资源和测试 fixture 提供仓库根路径，为 Windows MSVC 的开发、发布及测试程序嵌入 `Microsoft.Windows.Common-Controls` v6 清单。原生窗口策略按名称导入的 `GetWindowSubclass` 依赖该清单选择 v6 `comctl32.dll`，须按[验证指南](testing/window_policy.md#windows-msvc-链接产物)检查最终可执行文件。

使用支持 `build.build-dir` 的 Cargo 时，可在用户级 Cargo 配置中设置 `[build] build-dir`，或为各 worktree 的构建设置同一个 `CARGO_BUILD_BUILD_DIR`。将其指向专用缓存目录，例如主检出的 `tmp/shared-crates/`。最终程序仍保存在各 worktree 的 `target/` 中。机器专属路径留在本地配置。

共享内容是依赖编译结果、构建脚本输出和增量编译数据，区别于 `CARGO_HOME` 的源码下载缓存。工具链、目标平台、构建模式、依赖特性和编译参数一致时可复用匹配产物；同时构建可能等待共享目录锁，清理该目录也会移除其他 worktree 可复用的缓存。

构建和测试从对应 worktree 执行。Cargo 启动各应用包时，[工作区配置](../.cargo/config.toml)默认将 `BEVY_ASSET_ROOT` 指向仓库根目录，从同一 `assets/` 读取资源。需要指定其他资源根目录时，可在调用 Cargo 前设置 `BEVY_ASSET_ROOT`。配置细节见 [Cargo 构建目录](https://doc.rust-lang.org/cargo/reference/config.html#buildbuild-dir)。

Agent 执行相关构建检查、无窗口测试和[应用验收脚本](testing/app-acceptance.md)，按[测试指南](testing/README.md#agent-验证边界)选择实机验证方式并记录覆盖缺口。普通游戏由用户按[运行方式](../README.md#运行)启动。

### 日志排查

排查问题时保留原始日志。[玩家指南](player-guide.md#会话日志)说明如何找到日志文件，[会话日志架构](architecture/session_log.md)说明何时刷新写入。

需要记录视角角度和移动速度时，在启动游戏前设置 `RUST_LOG`。

```powershell
$env:RUST_LOG = "info,demo::camera=debug,demo::gameplay=debug"
```

排查结束后可移除当前终端的日志设置。

```powershell
Remove-Item Env:RUST_LOG -ErrorAction SilentlyContinue
```

## 临时文件管理

- 仓库内所有临时文件统一放在仓库根目录的 `tmp/` 下，可按任务或工具建立子目录。
- 使用工具前将临时输出和缓存目录配置到 `tmp/` 下。工具使用相对默认目录时，从对应的 `tmp/` 子目录执行并为输入指定正确路径，确保临时文件不散落到仓库其他位置。
- `tmp/` 加入版本控制忽略，临时文件不提交。正式交付文件、运行日志和正常构建产物按各自已有规则管理。
