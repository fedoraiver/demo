# 开发规范

本文规定开发者与 Agent 必须遵守的 ECS、输入、UI、调度、注释和日志要求，并提供构建配置与调试入口。当前组成和数据流见 [架构说明](architecture.md)，检查选择与覆盖边界见 [验证参考](testing/README.md)。

## 技术栈与版本

项目是用于探索和提升游戏制作水平的 demo，当前玩法尚未确定。技术上使用 Rust 与 Bevy，具体 edition、依赖版本和构建参数以 [Cargo.toml](../Cargo.toml) 与 [Cargo.lock](../Cargo.lock) 为准。

ECS 是架构模式，并无适用于所有引擎的统一强制规范。本文是本项目的工程约定；API 行为以对应版本的官方文档为准。使用与项目版本匹配的示例，不直接套用旧版 Bevy、Unity DOTS 或其他 ECS 框架的接口及限制。

## ECS 的职责划分

### Entity：实体只表示身份

- 使用 Bevy 的 `Entity` 标识实体，通过组件组合表达其能力和状态。
- 实体之间的引用使用 `Entity` 或 Bevy 关系组件，不持有其他实体组件的长期引用。
- 不建立包含全部状态与行为的 `GameObject` / `Actor` 对象层，不自行维护一套与 Bevy 重复的实体管理器。
- 实体可能被销毁；读取保存的实体引用时，按业务需要处理实体不存在或组件缺失的情况。
- 存档、网络协议等需要稳定标识时，使用独立的业务 ID，不把运行时 `Entity` 当作跨会话永久 ID。

### Component：组件承载实体数据

- 实体自身的状态定义为 `#[derive(Component)]` 的结构体或枚举；无数据的身份或能力标签使用标记组件。
- 按数据职责、访问模式和生命周期拆分组件，保持内聚。避免把位置、生命值、输入、渲染和 AI 等无关状态堆进一个巨型组件，也不要机械地将每个字段拆成组件。
- 组件可以提供构造、校验和只操作自身数据的辅助方法。每帧更新、跨实体交互、访问世界或外部服务等行为应由系统执行。
- 通过组件组合复用能力，避免用继承式层级或大型对象类型分支模拟实体种类。
- 同一业务状态应有明确的数据来源；优先复用 Bevy 已有组件，例如 `Transform`，避免无必要地维护重复数据。

### Resource / Local：明确共享范围

- 全局唯一、由多个系统共享的数据使用 `#[derive(Resource)]`，通过 `Res<T>` / `ResMut<T>` 访问，例如配置或全局统计。
- 属于某个实体的数据放在组件中，不用巨型全局资源中的实体列表替代 ECS 存储。确有需要的索引或缓存应明确维护与失效规则。
- 仅供单个系统保存的临时状态可使用 `Local<T>`。
- 不用可变静态变量或自建全局单例绕过 Bevy 的数据访问与调度机制。

### System：系统实现行为

- 系统使用职责明确的 Rust 函数，通过 `Query`、`Res`、`ResMut`、`Commands` 等参数声明所需数据。
- 使用组件组合和 `With<T>` / `Without<T>` 等过滤条件选择实体，避免依赖实体名称、固定 ID 或无关的类型判断。
- 查询仅请求所需数据；只读访问使用 `&T` / `Res<T>`，确需修改时才使用 `&mut T` / `ResMut<T>`，保留调度器并行执行的空间。
- 一个系统负责一个清晰的数据变换或流程步骤。复杂计算可提取为纯函数，由系统负责数据访问和结果写回。
- 查询访问冲突应通过拆分系统、明确互斥过滤条件或必要的 `ParamSet` 解决，不用 `unsafe` 或随意添加锁掩盖问题。
- 常规业务优先使用普通系统。确需独占 `&mut World` 的系统时，说明原因并限制其范围。

## 场景与 UI 装配规范

- 新增或修改场景、UI 和其他实体层级装配时，尽量采用 BSN（Bevy Scene Notation）风格的声明式代码，清晰表达组件、初始数据和子实体关系。
- 优先使用当前 Bevy 版本支持的 Rust 内嵌 `bsn!` 及可组合场景函数；按职责提取小型可复用结构，减少冗长、重复的逐实体装配代码。具体语法以项目依赖版本的官方文档为准。
- BSN 用于声明结构与初始数据；运行时状态变化、输入、交互和逐帧更新继续通过 ECS 系统或 Observer 实现，保持装配与行为职责清晰。
- 运行时动态构造、第三方 UI（如 Egui 工具面板）或当前 API 不适合 BSN 表达时，可以使用普通 `Commands` 或对应框架的原生 API，并在相关中文注释中简要说明设计原因。该优先级适用于本次涉及的新增或修改部分，存量代码按实际维护需要逐步调整。

## 输入处理规范

- 新增或修改输入处理时，优先使用项目已有的 `bevy_enhanced_input` 插件；先评估动作、绑定、上下文和动作事件能否表达需求，具体 API 使用项目依赖版本。
- 能通过插件表达的玩家操作，应复用插件的动作与上下文机制，不另建一套键鼠到业务行为的映射。动作响应通过 ECS 组件、资源或显式调度与玩法协作。
- 按控制上下文确定输入接收者，正确处理控制目标被销毁或缺少组件的情况。持续输入与一次性请求分别保存、消费，避免渲染帧与固定步数量不同导致丢失或重复执行。
- 确因窗口焦点、鼠标捕获、设备生命周期或插件能力限制需要直接读取底层输入或窗口事件时，在相关中文注释中说明原因，并限制处理范围；同一输入不能经两条路径重复触发业务行为。
- 输入处理顺序及命令可见性遵循下面的调度规范。有关当前动作路由和窗口捕获的实现，见 [当前架构](architecture.md)。

## UI 布局与高亮规范

### 保留文字的自然测量

在 Bevy 0.19.1 的横排布局中，为自动宽度的 `Text` 节点设置 `min_width: px(0)` 可能使测量宽度变为零。不能仅凭文字内容已写入实体、字体句柄存在或编译通过判断文字可见。

- 自动宽度的短文字默认保留自然测量，不在通用 `label`、`heading` 等文字辅助函数中统一设置零最小宽度，也不盲目套用其他 UI 框架的收缩规则。
- 容器与文字节点分别设计约束。容器可按需要使用 `min_width: px(0)`、有限宽度或滚动；长正文通过可用宽度和换行布局适配窗口。修复短标签时必须同时确认正文仍能换行，不能把所有节点改成固定宽度或禁止收缩。
- 修改共享文字控件后，检查所有使用场景，尤其是横排按钮标题、箭头、数字、键帽和固定尺寸装饰中的文字；不能只验收主菜单标题。
- 排查“空白控件”时核对 `Text` 内容、字体加载、`ComputedNode` 实际尺寸和 `TextLayoutInfo` 字形，再检查父容器约束与裁切；按证据定位，不能直接当成缺字体或占位设计。

### 区分悬停、导航与选中状态

焦点序号表示导航目标，不代表用户当前正在使用键盘或手柄；当前分类、默认操作和无交互装饰也不能代替悬停状态。

| 当前输入来源与状态               | 高亮规则                                                                    |
| -------------------------------- | --------------------------------------------------------------------------- |
| 鼠标模式，`Interaction::None`    | 恢复普通背景和边框，即使仍保存该按钮的焦点序号。                            |
| 鼠标模式，`Interaction::Hovered` | 仅高亮实际悬停按钮；按下反馈另由 `Pressed` 表达，释放或离开后恢复对应状态。 |
| 键盘／手柄实际导航               | 仅显示当前导航焦点；静止光标停在其他按钮上不能产生第二处悬停高亮。          |

- 使用明确的输入来源状态，样式系统统一读取来源、焦点与交互状态。鼠标模式只依据当前悬停／按下状态；导航来源由实际动作切换，不能因为 `MenuFocus` 存在就一直绘制焦点。
- 真实鼠标位置变化或点击可以接管输入来源，即使鼠标仍在同一按钮内且 `Interaction` 没有变化。移到空白或离开窗口也要切回鼠标模式，清除遗留导航高亮；页面重建产生的 `Hovered` 或 `Changed<Interaction>` 本身不能证明鼠标移动，不能抢走键盘焦点。
- 所有可交互按钮复用统一样式规则，包括主菜单、暂停、帮助返回、设置分类、调整箭头及 `Restore Defaults / Apply / Back`。当前分类如需表达选中状态，应采用与悬停可区分的样式，不能伪装成常驻悬停。
- 帮助编号等黄色装饰和 `Coming Soon` 占位不包含按钮动作、不进入导航列表，避免外观与可操作能力混淆。
- 页面重建、鼠标处理与样式更新遵循现有 `Build → Pointer → Style` 顺序，应用旧树销毁和新树生成的延迟命令后再读取交互，防止旧按钮状态或请求影响新页面。

相关实现入口为 [widgets.rs](../src/ui/widgets.rs)、[screens.rs](../src/ui/screens.rs) 和 [navigation.rs](../src/ui/navigation.rs)。具体检查方法见 [文字布局与高亮回归](testing/README.md#文字布局与高亮回归)；无窗口布局与状态测试不能替代用户对实际游戏窗口的视觉验收。

## 调度、通信与生命周期

- 使用 `add_systems` 注册系统。启动初始化使用 `Startup`，逐帧逻辑使用 `Update`；需要固定时间步的模拟逻辑使用 `FixedUpdate`，并使用相应时间步数据。
- 同一 Schedule 内有先后依赖的系统必须通过 `.before()`、`.after()`、`.chain()` 或 `configure_sets` 配置系统集之间的依赖。仅 `.in_set()` 不建立顺序；注册顺序、元组顺序和数据访问冲突也不能代替顺序约束。
- 顺序约束不会自动注册被引用的系统，也不能建立跨 Schedule 的顺序；核对相关系统是否注册，并按实际调度阶段设计数据流。
- 实体生成、销毁及组件增删等结构变更优先使用 `Commands`。它们是延迟操作，不要假设调用后立即能被当前系统的 `Query` 看到。
- 后续系统需要观察结构变更时，确保在两者之间应用延迟命令。常规调度配置中的 `.before()`、`.after()` 和 `.chain()` 支持自动插入同步点；自定义调度需核对实际配置，必要时使用 `ApplyDeferred`。
- 系统间的缓冲通信使用 `Message`、`MessageWriter`、`MessageReader`，并在 `App` 中注册消息；需要触发式响应时使用 `Event` / `EntityEvent` 与 Observer。两者语义不同，使用 Bevy 0.19.1 对应接口。
- `World::trigger` 在调用中触发 Observer；`Commands::trigger` 要等命令应用时才触发，不能假设立即生效。
- 跨系统协作通过组件、资源、消息或显式调度表达，不直接调用另一系统来隐式驱动流程。
- 初始化、退出和实体清理要与实际生命周期对应。默认消息缓冲不会永久保留，条件停用的读取系统可能漏读；必须跨停用期保留的业务状态应存入组件、资源或明确管理的持久队列。

### 固定模拟与逐帧显示的一致性

- 每个渲染帧可能执行零次、一次或多次固定步，不能假设本帧一定经过 `FixedUpdate`。运动积分与单次请求消费保留在固定模拟中；受本帧视角驱动的角色朝向、附件或持物的派生姿态，必须在相机更新与变换传播前于同帧同步。
- 同一 Schedule 内通过 `.chain()`、`.before()` 或 `.after()` 明确姿态依赖。跨 Schedule 必须核对实际主调度顺序与延迟命令应用时机，确保输入状态及持有关系在同步时可见；不能用跨阶段的顺序标注代替核对。
- 固定步与逐帧复用的系统只执行幂等的姿态同步：相同源状态应得到相同姿态，不额外积分运动、消费请求或触发交互。需要最新朝向的固定模拟仍保留其同步步骤，逐帧同步不能替代模拟依赖。
- 回归测试必须在实际 `app.update()` 返回后立即检查，不能先补跑固定步或姿态系统再断言。覆盖零固定步、多固定步及渲染频率高于固定频率的情况，同时检查业务根实体的 `Transform`、视觉子实体的 `GlobalTransform` 和解除关系后不再跟随的行为。

当前同步顺序见 [调度与模拟边界](architecture.md#调度与模拟边界)；测试组织与防止假通过的要求见 [避免测试掩盖帧间错位](testing/README.md#避免测试掩盖帧间错位)。

## 代码组织与性能

- 功能成长后按领域划分模块，并用 `Plugin` 封装系统注册、资源初始化和消息注册。`main.rs` 保持应用组装与启动职责。
- 小功能无需预建完整目录树；组件和系统可先放在同一功能模块中，复杂后再拆分。
- 优先批量查询处理实体，避免每帧全世界扫描、无必要的分配与克隆，以及频繁增删组件。
- 在适合的场景使用 `Added<T>`、`Changed<T>`、条件执行或消息驱动减少重复工作；不能因此遗漏必要的连续更新。
- 默认使用 Bevy 的存储与调度方式。只有测量表明确有需要时，才调整组件存储、并行迭代或缓存策略。

## 中文注释规范

- 新增或修改的代码应有必要的中文注释，说明模块、组件、资源和系统的职责，以及关键流程、边界条件和设计原因。代码标识符、API 名称和必要的英文术语保留原文。
- 日志消息、结构化字段名，以及代码定义的状态值、原因和错误提示统一使用英文；外部错误信息和文件路径保留原文。
- 遵循 Rust 注释格式：普通实现说明使用 `//`，类型、函数等条目的文档注释使用 `///`，模块或 crate 的文档注释使用 `//!`；文档注释放在对应条目的属性之前，模块文档注释放在模块开头。
- 对外公开的接口使用中文文档注释说明用途；必要时补充参数含义、返回值、错误条件和 panic 条件。文档中的代码示例使用 Rust 代码块，并与实际接口保持一致。
- 注释简洁、明了、直白，优先解释“为什么这样做”和不明显的行为；不逐行复述代码，不写空泛套话，不为显而易见的赋值或调用添加注释。
- 调度依赖、延迟命令的可见时机、日志与存档的处理规则等不易从代码看出的约束，应在相关位置用简短中文说明。
- 修改代码时同步更新相关注释，删除失效或误导性的说明，确保注释与实际行为一致。

## Git 提交规范

- 提交标题遵循 Conventional Commits 格式 `<type>[optional scope]: <description>`；标题语言按用户明确要求或仓库现有惯例确定，`type` 和 `scope` 保留英文。
- 提交正文统一使用中文，简洁说明具体改动、原因和验证结果；代码标识符、API 名称、文件路径及必要的英文术语保留原文。
- `BREAKING CHANGE`、`Closes` 等固定页脚标记保留原文；附带的自然语言说明使用中文。

## 游玩日志与调试

- 每次用户启动游戏游玩，都必须将本次会话的日志写入文件，不能仅输出到控制台。默认保存到 `logs/`，每次启动创建包含时间戳和唯一会话标识的新文件，保留历史日志，不覆盖前次记录。
- 日志从启动初始化开始，覆盖整个游玩过程；记录会话开始、版本与关键配置、正常退出，以及异常和错误上下文。运行期间及时写入，正常退出时刷新缓冲，尽量保留异常退出前的记录。
- 新增或修改功能时，同时补充有助于复现问题的日志。记录关键状态变化及其原因，例如场景切换、实体生成与销毁、生命值或资源变化、交互结果、任务进度，以及存档创建、写入、读取和失败。
- 状态变化日志应包含时间、级别、模块或系统、相关实体或业务 ID、变化前后值和触发原因；错误日志应包含操作、相关文件路径及错误信息，方便定位问题。
- 使用统一的日志设施，将 Bevy 日志与业务日志写入会话文件。日志配置和写入职责集中管理，避免各系统自行打开文件或重复初始化日志设施。
- 关键流程、状态变化和错误默认落盘；详细调试信息使用合适的日志级别。连续变化的高频数据按需采样或汇总，避免逐帧记录全部组件，但不能漏掉有调试价值的离散状态变化。
- 日志文件与游戏存档分别管理，运行日志不作为游戏状态存档使用。日志目录加入版本控制忽略；未经用户要求，不自动删除历史日志。

## 构建与调试

### 开发构建

在仓库根目录执行：

```powershell
cargo build --locked
```

Windows 输出程序为 `target/debug/demo.exe`。项目代码使用一级优化并保留完整调试信息，Bevy 等依赖使用三级优化。调试断言和整数溢出检查保持开启；优化可能使单步调试跳行或令部分变量不可查看。首次构建依赖耗时较长，后续构建可以复用缓存。

### 发布构建

```powershell
cargo build --release --locked
```

Windows 输出程序为 `target/release/demo.exe`。发布构建使用三级优化、Thin LTO 和单个代码生成单元，并移除调试信息；断言与溢出检查使用 Cargo 发布模式默认值。保留默认 panic 行为，便于正常清理资源和处理线程异常。

`--locked` 确保使用提交的依赖锁定文件，需要变化时直接报错。构建参数以 Cargo 文件为准。发布包必须携带完整的 `assets/`。

Windows MSVC 目标由根 [build.rs](../build.rs) 在链接时嵌入 `Microsoft.Windows.Common-Controls` v6 清单，覆盖开发、发布及测试程序。原生窗口策略按名称导入的 `GetWindowSubclass` 依赖该清单选择 v6 `comctl32.dll`；仅编译检查通过不能确认最终程序已携带清单，还需按 [验证指南](testing/README.md#windows-msvc-链接产物) 检查链接产物。构建脚本按目标平台与 ABI 判断，只向 Windows MSVC 传递清单链接参数，Windows GNU 与其他目标不使用这些参数。

使用支持 `build.build-dir` 的 Cargo 时，多个 worktree 可以共享编译中间产物，并保留各自 `target/` 中的最终程序。在各 worktree 被 Git 本地排除的 `.cargo/config.toml` 中，将 `[build] build-dir` 指向同一专用缓存目录，例如主检出的 `tmp/shared-crates/`；不要共享 `target-dir`，也不要提交机器专属路径。

共享内容是依赖编译结果、构建脚本输出和增量编译数据，区别于 `CARGO_HOME` 的源码下载缓存。工具链、目标平台、构建模式、依赖特性和编译参数一致时可复用匹配产物；同时构建可能等待共享目录锁，清理该目录也会移除其他 worktree 可复用的缓存。

构建和测试从对应 worktree 执行，用户启动游戏时也使用该工作目录，保证代码与资源一致。配置细节见 [Cargo 构建目录](https://doc.rust-lang.org/cargo/reference/config.html#buildbuild-dir)。

构建检查由 Agent 执行；游戏启动和实际游玩由用户完成。用户启动方式见 [README](../README.md#运行)，操作与配置见 [使用说明](usage.md)，开发检查见 [验证参考](testing/README.md)，实际窗口与听感按 [游戏手动验收](testing/game-acceptance.md) 由用户检查。

### 日志排查

日志位置和文件命名见 [使用说明](usage.md#会话日志)。当前写入机制见 [架构说明](architecture.md)；出现问题时结合相应会话文件分析，保留原始日志。

当前视角角度和世界移动速度以 `debug` 级别记录，每个采样系统每 0.5 秒最多采样一次；鼠标捕获及实际移动输入的离散变化以默认 `info` 级别记录。用户可在自行启动前设置：

```powershell
$env:RUST_LOG = "info,demo::camera=debug,demo::gameplay=debug"
```

该过滤设置提高上述模块的日志详细程度，仍需由用户自行启动游戏。采样包含相关实体、变化前后值和原因。排查结束后可移除当前终端会话的覆盖：

```powershell
Remove-Item Env:RUST_LOG -ErrorAction SilentlyContinue
```

## 临时文件管理

- 仓库内所有临时文件统一放在仓库根目录的 `tmp/` 下，可按任务或工具建立子目录。
- 使用工具前将临时输出和缓存目录配置到 `tmp/` 下。工具使用相对默认目录时，从对应的 `tmp/` 子目录执行并为输入指定正确路径，确保临时文件不散落到仓库其他位置。
- `tmp/` 加入版本控制忽略，临时文件不提交。正式交付文件、运行日志和正常构建产物按各自已有规则管理。
