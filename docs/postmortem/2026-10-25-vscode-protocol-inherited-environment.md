# Chrome 继承环境变量导致 VS Code 协议打开失败

## Executive summary（摘要）

2026-10-25，本机 ECS 架构图中的“在 VS Code 中打开”入口点击后没有可见反应，Chrome 控制台却显示已调用外部处理程序。排查确认 Chrome 进程携带 `ELECTRON_RUN_AS_NODE=1`，通过协议启动的 `Code.exe` 继承该变量，按 Node.js 模式解析参数并拒绝 `--open-url`。完整退出 Chrome、清除新进程的该变量并恢复原资料与页签后，源码定位恢复，用户确认手动点击正常。现有 URI 与页面交互回归未覆盖浏览器进程环境到编辑器启动的完整链路；长期经验是分段验证请求与实际接收结果，并控制桌面应用的启动环境。

## Impact and scope（影响与范围）

故障发生于本机 Windows 环境，排查时 Chrome 版本为 `156.0.8078.48`，VS Code 版本为 `1.143.1`。用户提供的控制台记录包含项目源码与 Cargo 依赖声明的协议请求，两类入口均报告没有打开编辑器；架构图页面仍能显示详情和生成源码定位。

发生条件是浏览器主进程已携带 `ELECTRON_RUN_AS_NODE=1`，且通过直接运行 `Code.exe --open-url` 的 Windows 协议处理程序启动 VS Code。清洁环境中的命令入口和 Windows 原生协议均能正确定位。本次恢复验证包含架构图中的项目源码入口及用户的手动点击确认，不代表全部依赖入口、浏览器和机器组合均完成验收。

## Evidence and timeline（证据与时间线）

1. 用户报告源码按钮点击无反应，随后提供 Chrome 控制台截图：其中出现 `Launched external handler`，请求包含 `vscode://file/D:/demo/src/main.rs:37:1` 及依赖声明定位。该记录证明浏览器已调用外部处理入口，不能证明 VS Code 已接收并打开文件。
2. 检查真实生成页脚本，确认有效源码链接没有被 `preventDefault`，点击后链接仍在页面中。隔离 Chrome 的点击探针也观察到 `Page.frameRequestedNavigation`，原因为 `anchorClick`，目标为正确的 VS Code URI。源码链接全量审计未发现无效定位。
3. 分别使用 VS Code 命令入口和 Windows 原生协议请求定位项目文件，编辑器保存的文件与光标状态符合请求，用户也确认命令入口能打开 `src/main.rs` 第 `37` 行。由此将排查重点转向浏览器调用与清洁环境调用的差异。
4. 仅定向读取故障 Chrome 进程的 `ELECTRON_RUN_AS_NODE`，实际值为 `1`。在受控子进程环境中设置同一变量，运行 `Code.exe --open-url -- <源码 URI>`，得到退出码 `9` 和错误 `Code.exe: bad option: --open-url`，复现了编辑器启动失败。
5. 经用户允许，完整退出 Chrome，在新进程环境中移除该变量并恢复原资料与页签。复查新 Chrome 进程时，该变量不存在；从架构图点击后，VS Code 保存的光标由对照位置第 `38` 行回到目标第 `37` 行、列 `1`。
6. 用户确认重启后的手动点击已经能正常跳转。事故排查时，架构图基线测试 `433` 项通过，源码入口相关测试 `37` 项复查通过；后者与基线存在覆盖重叠，不能累加为 `470` 项独立测试。这些测试通过也没有单独证明外部编辑器启动成功。

关键复现条件、错误与恢复结果已保留在正文。原始探针、日志及状态记录位于仓库根 `tmp/ecs-architecture/2026-10-25-vscode-open/`，仅作本地补充证据，不作为长期记录的唯一依据。

## Root cause and missed safeguards（根因与漏检环节）

`ELECTRON_RUN_AS_NODE` 会改变 Electron 可执行程序的运行模式。故障浏览器通过 Windows 协议处理程序启动 `Code.exe` 时，把自身的该变量传入了子进程。此时 `Code.exe` 按 Node.js 命令行模式处理参数，无法接受桌面应用入口使用的 `--open-url`，因此在打开编辑器之前退出。页面发出的 URI、当前用户的协议注册及 VS Code 的文件行列解析在对照验证中均正常。

现有 [源码入口测试](../diagrams/tests/source-editor.test.mjs) 和 [源码页测试](../diagrams/tests/source-viewer.test.mjs) 主要验证 URI 编码、根目录配置、生成脚本及页面事件；最小 DOM 无法验证 Windows 如何启动编辑器。浏览器导航事件与 `Launched external handler` 也只能证明请求到了对应边界。命令正常返回可能仅表示请求已传给现有进程，同样需要核对编辑器实际打开的文件与行列。

诊断前段较多时间用于检查页面点击、URI 格式及源码记录。取得浏览器已调用外部处理程序的证据后，应尽早比较浏览器点击、系统协议与命令入口，随后检查失败调用方的必要启动环境。这样能更快找到差异，避免在已经通过验证的页面层持续扩大检查范围。

已确认变量存在及其失败机制，尚未确定最初由哪个启动器把它带入 Chrome。现有证据不足以将注入来源归因于 Live Server、Codex 或某个浏览器扩展。

## Prevention（防复发措施）

- **已完成的恢复**：完整退出受影响的 Chrome，从移除 `ELECTRON_RUN_AS_NODE` 的子进程环境重新启动，并恢复原资料和页签。该修复没有修改系统全局环境或 Windows 协议注册。刷新页面、关闭单个页签或向已有浏览器进程新开窗口，都不会清除主进程已经继承的环境。
- **桌面启动约定**：后续维护普通桌面模式的 Electron 应用启动器，或会通过协议调用这类应用的浏览器启动器时，在对应子进程环境中移除该变量。保留确实依赖 Node.js 模式的 CLI 调用环境，避免全局清理造成另一类启动故障。
- **分段验收**：按 [架构图源码定位验证](../testing/README.md#架构图源码定位验证) 分别记录页面请求和编辑器接收结果，最终核对实际文件、行、列。URI 检查、浏览器日志、命令退出状态与用户实际验收各自保留其证明范围。
- **诊断操作**：优先使用用户指定的 Chrome 插件检查页面，按需定向检查环境变量，避免导出完整进程环境。涉及完整重启浏览器时，先说明对现有页签的影响并取得允许，再恢复原资料和页面。
- **剩余缺口**：本次完成的是进程环境恢复，尚未修正变量最初注入的启动器，也未增加覆盖真实浏览器继承环境的自动化回归。再次从携带该变量的环境启动浏览器仍可触发同一机制；后续若确认具体启动入口，应在该入口落实子进程环境清理并补充针对性验证。
