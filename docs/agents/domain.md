# 领域文档读取约定

当前仓库是一个游戏原型，使用 [当前架构](../architecture.md) 作为实现概览。领域术语和架构决策在实际需要时补充；本文件负责告诉技能应读取哪些已有资料。

## 当前读取顺序

1. 读取根 [Agent 开发指南](../../AGENTS.md) 指定的必读工程规范。
2. 读取 [当前架构](../architecture.md)，定位任务涉及的模块和数据流，再核对相关源码。
3. 涉及玩法目标时读取 [游戏设计](../game-design.md) 和相关 Issue，区分已确认设定与建议。
4. 如果已有 `CONTEXT.md` 或 ADR，按下方规则继续读取。

目前尚无 `CONTEXT.md`、`CONTEXT-MAP.md` 或 ADR。它们缺失时静默继续，依据已有架构、代码和开发指南开展工作，不将缺失视为阻塞，也不为目录完整而创建占位文件。

## 领域文档扩展后的读取规则

- 单上下文项目存在根 `CONTEXT.md` 时，读取它以及 `docs/adr/` 中与任务有关的决策。
- 出现真实的多个上下文后，使用根 `CONTEXT-MAP.md` 索引各上下文的职责、源码范围、`CONTEXT.md` 和 ADR 路径；先读取索引，再读取任务涉及的上下文。
- 子项目 ADR 默认路径为 `src/<context>/docs/adr/`，实际路径以索引为准；同时读取相关的全局 `docs/adr/` 决策。
- 跨上下文任务读取所有相关资料，并明确交互边界。采用多上下文布局时，同步更新本文件和根 AGENTS 的读取入口。

只有真实术语、边界和决策需要记录时，才建立相应领域文档。已采用的具体布局和消费规则由实际资料维护。

## 术语与决策

Issue、重构方案、诊断假设和测试名称采用相关 `CONTEXT.md` 中定义的术语，避免使用文档明确排除的同义词。

需要的概念未记录时，先核对代码和既有用语；确有缺口时留给 `grill-with-docs` 等领域澄清流程，不自行发明领域定义。

方案与现有 ADR 冲突时，明确指出冲突的 ADR、原因和影响，不静默覆盖既有决策。所有游戏逻辑仍须遵循根 [Agent 开发指南](../../AGENTS.md) 与 [开发规范](../development.md)。
